### D-84. 초등 영어회화 3건 개선 — 이전 문장 이동·produce 질문 자동 재생·TTS 음성 품질
- **배경**: 사용자가 실제로 써보고 세 가지를 지적: ①챕터에 들어가면 다음 문장으로만
  갈 수 있고 이전 문장으로 돌아갈 수 없다. ②`type: "produce"`(질문·답변형) 문제에서
  질문 문장을 소리 내어 들려주는 기능이 없다(버튼을 눌러야만 들림 — 실제 대화라면
  질문이 먼저 들리는 게 자연스럽다). ③듣기 음성이 기계음처럼 부자연스럽다.
- **① 이전 문장 이동**: `basic-conversation/screens.js`의 `showCard()`와
  `elementary-conversation/screens.js`의 `showRepeatCard()`/`showProduceCard()` 모두
  현재 문장 인덱스가 0보다 클 때만 "◀ 이전 문장" 버튼(기존 `.retry-btn` 재사용, 새
  CSS 없음)을 보여준다. elementary 쪽은 `advance()`와 대칭인 `prev()` 헬퍼를 추가해
  `st.index -= 1` 후 `showCard()`를 다시 부른다 — 복습 모드(`reviewMode`)로 필터링된
  `sentences` 배열 안에서도 그대로 동작한다(인덱스는 항상 현재 활성 배열 기준). basic
  쪽은 기존 "다음 문장" 핸들러와 대칭으로 인라인 처리(그쪽 파일 자체가 아직 헬퍼로 안
  뽑혀 있어 굳이 새로 안 뽑았다).
- **② produce 질문 자동 재생**: `showProduceCard()` 끝에 `if (supportsSpeech())
  speak(card.text, 1)`를 추가해, 카드가 뜨면(처음 진입·이전/다음 이동 전부 포함)
  질문을 한 번 자동으로 읽어준다. "repeat" 카드는 그대로 자동 재생을 안 한다 — 그
  카드는 아이가 듣기 버튼을 눌러 스스로 페이스를 조절하는 게 원래 설계 의도라
  건드리지 않았다.
- **③ TTS 음성 품질**: `js/learning/speech.js`의 `speak()`에 `pickVoice(lang)`을
  추가 — `speechSynthesis.getVoices()`에서 해당 언어의 음성 중 `localService`가
  아닌(네트워크) 음성을 우선 골라 `utterance.voice`에 지정한다. 기기 내장 로컬 음성은
  대체로 기계음에 가깝고, Chrome의 "Google US English" 같은 네트워크 음성이 훨씬
  자연스럽다는 게 흔한 차이라 이 우선순위를 그대로 썼다. 특정 음성 이름을 하드코딩하지
  않은 이유는 기기·브라우저마다 음성 목록이 달라 이름 매칭이 깨지기 쉬워서다 —
  "로컬이냐 아니냐"만 보는 게 기기 간 이식성이 높다. 음성 목록이 아직 비동기 로드
  전이면(Chrome 특성) `matching`이 빈 배열이라 `voice`가 `null`로 남고, 그때는 그냥
  브라우저 기본 음성으로 재생된다 — 별도 대기 로직은 추가하지 않았다(다음 재생부터는
  목록이 채워져 있어 자연스럽게 좋은 음성으로 바뀐다). `speak()`가 두 도구
  (basic-conversation·elementary-conversation) 공용이라 이 개선이 자동으로 둘 다에
  적용된다.
- **검증**: `npm test` 147/147(로직 변경 없음, 순수 UI/음성 선택 추가). 헤드리스
  브라우저: (1) 두 도구 모두 1번째 문장엔 이전 버튼이 없고 2번째부터 생기는지, 클릭
  시 인덱스가 정확히 하나 줄어드는지 확인. (2) produce 카드에서만
  `speechSynthesis.speak()`가 자동 호출되고 repeat 카드에서는 호출되지 않는지 확인
  (중급 6문장 중 정확히 2번 — produce 문장 개수와 일치). (3) 콘솔 에러 없음. 음성
  품질 자체(③)는 실제 사람 귀로 들어야 판단 가능해 헤드리스로는 "voice 선택 로직이
  던지지 않고 동작하는지"까지만 확인했다 — 실제 자연스러움은 배포 후 실기기 확인이
  필요하다.
- **배포 후 확인 필요**: 실기기(특히 안드로이드 Chrome)에서 듣기 버튼을 눌러 음성이
  실제로 예전보다 자연스러워졌는지 확인. 기기에 따라 네트워크 음성이 아예 없을 수도
  있어(오프라인이거나 OS에 TTS 엔진이 로컬만 설치된 경우) 그때는 개선 체감이 없을 수
  있다 — 그 경우도 에러 없이 기존 동작(로컬 음성)으로 조용히 폴백된다.

### D-85. 문장 자연스러움 전수 검토 + produce 예시 답안 보강
- **배경**: 사용자가 외부 첨삭 도구 캡처를 공유 — "I shouldn't spend too much time on games."
  (좋아하는 것 챕터, 심화)가 문법적으로는 맞지만 원어민이라면 "playing games"처럼
  동명사를 붙여 쓴다는 지적. "이런 문장이 더 있으면 고치고, produce 문장엔 유사·대안
  표현도 같이 적어주면 도움이 되지 않겠냐"고 물어서, repeat 문장은 오류 교정만(채점이
  문장 하나 기준이라 대안 표현을 새 필드로 못 넣는다 — D-84 근처에서 이미 정리한
  제약), produce 문장은 이미 있는 `sample`(예시 답안) 배열을 보강하는 쪽으로 방향을
  잡고("그렇게 하자") 진행했다.
- **문장 교정**: `elementary-conversation/data.js` 300문장 + `basic-conversation/data.js`
  362문장을 전부 읽고 훑었다. 실제로 고친 건 3곳뿐(둘 다 elementary-conversation —
  basic-conversation은 애초에 어린이 방송 대사를 참고해 지은 문장이라 이미 구어체에
  가까웠다, D-65):
  1. `shouldnt-spend-too-much-time-on-games` → `shouldnt-spend-too-much-time-playing-games`
     로 id까지 같이 바꿈. "on games"를 "playing games"로.
  2. `why-do-you-like-school`(학교 가는 날 챕터, 심화): "Why do you like or not like
     going to school?" → "Why do you like or dislike going to school?" (hint도
     "I like/don't like" → "I like/dislike"로 맞춤). "or not like"보다 "or dislike"가
     원어민이 훨씬 자주 쓰는 짝이다.
  3. `why-do-you-like-pe`(체육 시간 챕터, 심화)도 같은 패턴 — "Why do you like or not
     like PE?" → "Why do you like or dislike PE?" (hint 동일하게 수정).
  전수 검토라 아이디도 문장도 안 바뀐 나머지 297개는 원어민 구어체 기준으로도 자연스럽다고
  판단해 그대로 뒀다.
- **produce 예시 답안 보강**: `type: "produce"`인 문장 60개(15챕터 × 챕터당 4개 —
  중급 2 + 심화 2) 전부 `sample` 배열에 세 번째 답안을 하나씩 추가했다. 기존 2개는
  대체로 "A and B" 식 완결문 두 개였는데, 세 번째는 실제 대화체에서 더 자주 쓰는 짧은
  형태("Just my backpack, really.", "Probably PE, because I love moving around.",
  "Honestly, it depends on my mood." 등 — Just/Probably/Honestly로 시작하는 축약형·
  헤지 표현)로 골라, 완결문만 보여주는 것보다 실제 대화 감각에 더 가깝게 했다.
  `test/learning.elementary.test.js`의 produce 검사가 "sample 최소 1개"만 요구해서
  기존 테스트 수정 없이 통과한다.
- **검증**: `npm test` 147/147. `node -e`로 produce 문장 60개 전부 `sample.length ===
  3` 확인, 챕터 내 id 중복 0건(재확인). 헤드리스 브라우저로 교정된 문장이 실제 카드에
  렌더되는지, 콘솔 에러 없는지 확인.

### D-86. produce 카드 마이크 버튼 레이아웃 깨짐 수정
- **배경**: 사용자가 실기기 스크린샷 공유 — produce 카드의 "🎤 내 생각 말하기" 버튼이
  아래 "✓ 다음 문장"/"◀ 이전 문장" 버튼과 겹쳐 보였다. `.btn-mic`가 84px 고정 원형
  (`width`/`height`/`border-radius: 50%`)이라 이모지 하나(`🎤`, basic-conversation과
  repeat 카드가 쓰는 형태)만 가정하고 있었는데, produce 카드만 긴 텍스트("🎤 내 생각
  말하기")를 넣으면서 원 밖으로 줄바꿈되어 아래 요소를 덮었다.
- **수정**: `.btn-mic`(원형, 아이콘 전용)는 그대로 두고, `.btn-mic-labeled` 변형
  클래스를 추가해 텍스트가 있는 경우만 `width: auto`·`border-radius: 999px`(알약
  모양)로 늘어나게 했다. 배경·그림자는 `.btn-mic`에서 그대로 물려받고 크기·모양만
  덮어쓴다. `showProduceCard()`의 마이크 버튼에만 `btn-mic btn-mic-labeled` 두 클래스를
  같이 붙였다 — repeat 카드(`🎤`만)와 basic-conversation은 그대로 원형 유지.
- **검증**: `npm test` 147/147(로직 무변경). 헤드리스 브라우저를 모바일 뷰포트(390×844)로
  띄워 produce 카드 진입 후 마이크 버튼과 "다음 문장" 버튼의 바운딩 박스가 겹치지
  않는지 확인, 스크린샷으로도 육안 확인.

### D-87. 각 학년 6번째 챕터 + 다중 턴 대화 도구(`dialogue`) 신설
- **배경**: 학년 3단계가 다 찬 뒤 남겨둔 두 갈래 — (1) 각 학년에 챕터 더 늘리기,
  (2) §3-7이 오래 미뤄둔 진짜 다중 턴 대화형 도구 — 를 사용자가 **둘 다** 진행하기로
  확정("1,2부터 진행").
- **(1) 각 학년 6번째 챕터**: 저학년 `급식 시간`(🍚)·중학년 `건강과 습관`(💪)·고학년
  `미디어와 기술`(📱)을 같은 틀(기본 10·중급 6·심화 4 = 20문장)로 추가 —
  3개 학년·18챕터·360문장이 됐다. 앞선 6번째 챕터들(좋아하는 것·우리 동네·여행과 경험)과
  달리 셋 다 **새 문법을 하나씩 도입**했다: G18(want to), G19(빈도부사
  always/usually/sometimes/never), G20(수동태 be + 과거분사). 순수 재사용으로 두지 않은
  이유는 세 소재의 핵심 표현이 기존 문법 목록에 아예 없었기 때문이다 — "~하고 싶다"는
  저학년이 제일 많이 쓰는데 G1~G6에 없었고, "얼마나 자주"는 습관 얘기의 핵심인데
  G7~G11·G16에 없었고, "~로 만들어졌다"는 기술·미디어 소재에서 자연스럽게 나오는데
  G12~G15·G17에 없었다. 번호는 D-83 규칙대로 학년과 무관하게 전체 최대값 다음으로 이어 붙임.
- **(2) `js/learning/dialogue/` 신설**: §3-7이 "기존 도구를 고치기보다 새 도구로 추가하는
  쪽이 맞아 보인다"고 미리 정해둔 그대로 따랐다 — basic/elementary는 "정해진 문장 하나를
  얼마나 똑같이 따라 했는가"(Levenshtein)를 재는 구조라, 주고받는 대화를 끼워 넣으면 두
  모델이 한 폴더에 섞인다. 모델:
  - 장면(`SCENES`) 하나 = 대화 하나. **학년·단계 층을 두지 않았다** — 대화는 상황 자체가
    난이도라, 문장 단위 도구처럼 3단계로 쪼개면 같은 대화를 세 번 써야 한다. 그래서
    elementary(학년 → 챕터 → 단계 → 문장)보다 두 단 얕다(장면 → 턴).
  - `turns` 배열에 `role: "partner"`(상대 대사 — 자동 재생 + "내 차례로 →")와
    `role: "you"`(내 차례 — 영어 정답 문장을 안 주고 한국어 지시문 + `hint`만 주고,
    STT 후 `sample`과 비교해 자가평가)가 번갈아 온다.
  - **유사도 채점 없음**: elementary의 produce 문장과 같은 이유(정답이 여럿이라 잴 대상이
    없다). 자가평가만 `weak`에 반영 — 마이페이지 집계(D-79)는 개별 도구를 import하지 않고
    `state.learning` 모양만 보므로 이 도구도 코드 수정 없이 자동으로 잡힌다.
  - **지나온 턴을 화면 위에 로그(`.dialogue-log`)로 쌓는다**: 대화는 앞 맥락이 있어야 내
    차례를 채울 수 있어서, 카드 하나만 띄우는 문장 단위 도구와 달리 이전 대사를 남긴다.
    내가 말한 것(STT 결과)도 `turn.said`에 담아 그 자리에 넣는다.
  - 장면 4개(친구와 약속 잡기·처음 만난 친구와 인사·가게에서 물건 사기·식당에서 주문하기),
    각 8턴(상대 4 + 내 차례 4).
- **분기(branching)를 일부러 안 넣었다**: 자유 발화를 알아듣고 갈래를 고르려면 STT 결과를
  의미로 해석해야 하는데, 브라우저 내장 STT 인식률로는 "조금 다르게 말했더니 대화가 산으로
  가는" 실패가 훨씬 잦다. 대신 한 줄기로 흐르되 내 차례에서 뭘 말하든 상대 대사가 자연스럽게
  이어지도록 썼다 — 분기형이라기보다 역할극(role-play)에 가깝다. 진짜 분기가 필요해지면
  그땐 STT가 아니라 선택지(고르기) 기반으로 다시 볼 것.
- **재사용한 것**: `speech.js`(speak/listen)·`.cover`/`.test-card`/`.retry-btn`/`.btn-mic
  .btn-mic-labeled`(D-86)·`learning` 테마·`saveLearningProgress()`를 그대로 썼다. 새로 추가한
  CSS는 `.dialogue-log`/`.dialogue-line`/`.cover.cover-you` 셋뿐이다.
- **검증**: `npm test` 147/147(`test/modules.test.js`의 화면 목록에 `dialogueScreens` 추가 —
  화면 id/경로 중복 검사가 새 도구까지 함께 본다). 모바일 뷰포트(390×844) 헤드리스 브라우저에
  가짜 `SpeechRecognition`을 주입해: 학습 목록에 카드 노출 → 장면 4개 → 1턴 상대 대사(이전
