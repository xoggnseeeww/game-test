### D-103. DAY 확인 문제·빈칸 채우기가 같은 단어를 중복 채점해 SRS 간격이 부풀던 버그 수정
- **배경**: 사용자 요청으로 D-98~D-102 전체를 다시 훑었다(오류 검토 + 개선점 파악 후 수정 →
  메인 머지). 가장 심각했던 것은 **DAY 화면 안에서 같은 단어가 세 번 채점되고 있었다**는 것.
- **증상**: `renderVocabDay()`의 흐름은 단어 카드(👍/😅 자가평가) → 확인 문제(4지선다) →
  빈칸 채우기(철자) 순인데, 셋 다 `gradeWord()`를 불러 **같은 단어의 SRS 엔트리를 계속
  다시 채점**했다. 카드에서 "good"(reps 0→1, ivl=1, due=내일)까지는 의도대로였지만, 곧이어
  확인 문제에서 "good"을 한 번 더 받으면 reps 1→2·ivl=3(due 3일 뒤)으로, 빈칸까지 마치면
  reps 2→3·ivl = 3×ease ≈ 8(due 8일 뒤)로 튀었다. **DAY 하나를 처음부터 끝까지 도는
  몇 분 사이에, 아직 하루도 안 지난 단어가 "8일 뒤에나 다시 보여줄 단어"가 돼 있었다.**
  D-99·D-101·D-102에서 사용자에게 "내일 다시 올라와요"라고 설명한 것과 실제 동작이
  어긋나 있었던 셈이다 — 화면 문구는 맞았지만 그 문구가 가리키는 값 자체가 잘못 계산되고
  있었다.
- **왜 지금까지 안 잡혔나**: `state.vocab.cards`는 세션 메모리라 새로고침 전에는 눈에
  잘 안 띄고, 헤드리스 검증도 지금까지는 "화면이 뜨는가/문구가 맞는가"만 확인했지 실제
  스케줄 값(`reps`·`ivl`)을 페이지 안에서 직접 읽어본 적이 없었다.
- **원인**: SM-2류 스케줄은 "실제로 날짜가 벌어진 recall"에만 의미가 있다 — `cur.reps`가
  이전 성공 횟수를 나타내고 그 횟수만큼 간격이 기하급수로 늘어나는데, 같은 세션 안에서
  초 단위로 여러 번 "성공"을 기록하면 시간 경과 없이 reps만 쌓여 간격 계산이 그 전제를
  잃는다.
- **수정**: DAY 화면에서는 **카드 자가평가만 SRS를 건드린다**. 확인 문제(`pick()`)와 빈칸
  채우기(`grade()`)에서 `gradeWord()` 호출을 제거했다 — 정답/오답 판정과 `st.wrong`/
  `correctCount`(DAY 정답률·"틀린 단어만 다시 보기" 진입로)는 그대로 남아 있으니 DAY
  화면의 다른 기능은 전부 그대로다. "틀린 단어만 다시 보기"로 카드 자가평가를 다시 하는
  경로는 그대로 뒀다 — 그건 사용자가 명시적으로 고른 재학습이라 다시 채점되는 게 맞다.
  "오늘 학습"(`/today`)은 손대지 않았다 — 거기는 큐의 항목 하나가 정확히 한 번만
  `advance()`를 통해 채점되는 구조라 애초에 이 버그가 없었다.
- **덤으로 고친 것 셋**(같은 리뷰에서 발견):
  1. **로그인 동기화 알림 경쟁**: `initVocabSync()`가 설정(`vocab_settings`)과 일정
     (`vocab_progress`) 두 요청을 병렬로 보내면서, 화면 재렌더 알림(`notifyLearningSync`)은
     일정 쪽 요청에만 붙어 있었다 — 설정 요청이 더 늦게 끝나면 방금 로그인한 사용자의
     "하루 목표" 선택이 화면에 반영 안 된 채로 남을 수 있었다. 두 요청을
     `Promise.allSettled`로 묶어 **둘 다 끝난 뒤 한 번만** 알리도록 고쳤다.
  2. **탭 제목이 개명 전 이름을 그대로 두고 있었다**: D-101에서 화면을 "오늘 복습"에서
     "오늘 학습"으로 바꿨는데, `civilVocabScreens`의 `title`(브라우저 탭 제목)은 "오늘
     복습"에 머물러 있었다.
  3. **오늘 큐의 빈칸 모드에 null 방어가 없었다**: DAY의 빈칸 흐름(`startCloze`)은 예문에서
     표제어를 못 찾는 단어(`makeCloze()`가 null)를 미리 걸러내는데, 오늘 큐 쪽은 그 방어가
     없어서 그런 단어를 만나면 화면이 죽을 수 있었다. 지금 200단어는 전부
     `test/learning.vocab.test.js`가 통과를 보장하지만, 8000개로 늘어날 콘텐츠의 방어선으로
     오늘 큐도 null이면 고르기 모드로 자동 대체하게 했다.
- **검증**: 페이지 안에서 `state.js`를 직접 동적 import해 `state.vocab.cards`의 실제
  `reps`/`ivl` 값을 읽는 헤드리스 테스트를 새로 만들었다(지금까지는 화면 문구만 봤지 값
  자체를 검증한 적이 없었다). DAY 1(50단어)을 카드 → 확인 문제 → 빈칸까지 전부 마친 뒤
  `reps === 1 && ivl === 1`(=내일)이 유지되는 것을 확인했다. **버그를 되살려 빨간불도
  확인했다** — gradeWord 호출을 되돌리면 확인 문제 단계에서 이미 `reps`가 흔들리고
  (테스트가 무작위로 첫 보기를 눌러 오답이 섞이면서 `lapses`까지 늘어나는 걸로 나타났다),
  복구 후 다시 통과. `npm test` 217/217(순수 함수 쪽은 이번 수정과 무관해 그대로), 기존
  헤드리스 스위트·`scripts/verify.cjs` 재확인 통과.
- **손대지 않은 것**: 로그아웃 후 같은 브라우저 탭에서 다른 계정으로 로그인하면 첫 계정의
  로컬 세션 데이터(`state.vocab.cards` 등)가 초기화되지 않고 새 계정과 병합돼 버릴 수 있는
  경로를 리뷰 중에 함께 발견했다. 이건 `js/learning/cloud.js`(학습 진행률)·NumPath 마을
  동기화에도 똑같이 있는 **앱 전체의 기존 패턴**이라, 이번 어휘 도구만 따로 고치면 세
  동기화 모듈의 동작이 서로 달라진다. 별도로 논의해서 세 곳을 한 번에 정리하는 게 맞다고
  보고 이번 범위에는 넣지 않았다.

### D-104. 로그아웃해도 로컬 진행률이 안 지워져 다른 계정으로 로그인하면 섞이던 버그 수정
- **배경**: D-103 리뷰 중 발견해서 "손대지 않은 것"으로 남겨뒀는데, 사용자가 "치명적인
  오류인데 앱 전체의 기존 패턴이라도 수정해야 될 것 같다"고 판단해 이번에 바로 고쳤다.
- **증상**: `js/learning/cloud.js`(문장 도구 진행률)와 `js/learning/civil-vocab/cloud.js`
  (어휘 일정)의 로그인 동기화 로직이 로그아웃(`user === null`)을 감지하면 `syncedForUser`만
  `null`로 되돌리고, **로컬 state는 그대로 뒀다.** 그래서 같은 브라우저 탭에서 계정 A로
  공부하다 로그아웃하고 계정 B로 로그인하면: 로그인 이벤트가 오자마자 `mergeProgress()`/
  `mergeVocabCards()`가 "로컬(=방금 나간 A의 진행률)"과 "B의 서버 값"을 합쳤다. 병합
  규칙이 "더 진행된 쪽" 또는 "더 최근 응답"을 남기는 것이라, A가 더 많이 공부했거나 더
  최근에 응답했으면 **A의 진행률이 그대로 B 계정에 업서트됐다** — 서로 모르는 두 사람이
  같은 기기(도서관 PC, 학원 공용 PC, 가족 공유 태블릿)를 오가며 쓰면 실제로 벌어질 수
  있는 사고다.
- **왜 지금까지 안 잡혔나**: 두 모듈 모두 "순수 함수(`mergeProgress`/`mergeVocabCards`)만
  `node --test`로 검증하고, 나머지는 Supabase 클라이언트에 묶여 브라우저에서만 돈다"는
  이유로 로그인/로그아웃 흐름 자체는 테스트가 없었다(주석에도 그렇게 적혀 있었다). 헤드리스
  회귀도 이 샌드박스에서는 Supabase CDN이 막혀 실제 로그인·로그아웃 왕복을 재현할 수 없다.
- **수정**: 로그아웃을 감지하면(`syncedForUser`가 `null`이 아니었다 = 방금 전까지 어떤
  계정의 데이터가 로컬에 실려 있었다) 그 데이터를 **지운다**.
  - `js/learning/cloud.js`: `state.learning = {}`
  - `js/learning/civil-vocab/cloud.js`: `state.vocab.cards = {}` · `state.vocab.days = {}` ·
    `state.vocab.newPerDay = DEFAULT_NEW_PER_DAY`(하루 목표도 계정을 안 타는 값이 아니므로
    같이 되돌린다 — 안 그러면 자기 설정이 없는 다음 계정이 방금 나간 계정의 목표를 물려받는다)
  - **한 번도 로그인한 적 없는 세션은 그대로 둔다**(`syncedForUser`가 원래부터 `null`인
    경우는 지우지 않음) — 안 그러면 "로그인 전에 공부해두고 나중에 로그인해서 서버로
    올린다"는 이 앱의 핵심 흐름(D-68, D-100)이 깨진다. 로그아웃 이벤트와 "로그인한 적
    없음"을 구분하는 게 이 수정의 핵심이다.
- **테스트 가능하게 리팩터링**: 두 모듈 다 로그인 이벤트 콜백(`sync`)이 `loadCloudAuth()`로
  받아온 실제 CDN 클라이언트에 클로저로 묶여 있어 순수 함수가 아니었다. `cloud` 클라이언트를
  **인자로 받는** `makeSyncHandler(cloud)`로 빼서, `initLearningSync()`/`initVocabSync()`는
  실제 클라이언트로 이 함수를 호출하기만 하고, `node --test`에서는 최소한의 가짜
  `cloud`(로그인 상태를 흉내내는 `_login()`/`_logout()`, `select/eq/order/range/maybeSingle/
  upsert`를 체이닝만 흉내내는 가짜 `supabase.from()`)로 실제 시나리오를 검증한다.
  `syncedForUser`도 모듈 전역에서 `makeSyncHandler`의 클로저로 옮겼다 — 안 그러면 테스트
  여러 개가 그 상태를 공유해서 서로 오염시킨다.
- **검증**: 두 모듈 각각에 시나리오 테스트를 새로 만들었다 — "A로 로그인 → 로컬에 진행이
  많이 쌓임 → 로그아웃 → 로컬이 비어야 함 → B로 로그인 → B의 서버 값만 보여야 함(A의 값이
  안 섞여야 함)", "로그인한 적 없는 세션은 아무것도 안 지운다", "핸들러 인스턴스끼리
  `syncedForUser`가 안 샌다". `npm test` **222/222**(문장 도구 3개·어휘 도구 2개 추가).
  **버그를 되살려 빨간불도 확인**했다 — 로그아웃 분기의 초기화 코드를 되돌리면 "B로
  로그인했는데 A의 로컬 값이 섞여 들어왔다" 검사가 정확히 실패한다. 이 샌드박스에서는
  실제 Supabase 로그인 왕복을 재현할 수 없어 헤드리스 브라우저 검증은 못 했다 — 순수
  로직으로 옮긴 이 테스트가 지금 낼 수 있는 가장 강한 증거다.
- **배포 후 확인 필요**: 실기기에서 계정 A로 로그인해 몇 개 학습 → 로그아웃 → 계정 B로
  로그인 → 마이페이지·어휘 인트로가 **B 자신의** 진행만 보여주는지(A의 흔적이 안 남는지).

### D-105. MD 문서 재편 — 자동 로드 42k → 9k 토큰, 이력은 인덱스+월별 아카이브로
- **배경**: 사용자 요청 — "md파일도 정리 한번 하자. 장기적으로 관리하기 위한 최적화 진행하고,
  분할 및 병합 정리 및 요약 부탁해. 작업시 토큰 최적화 될 수 있도록 고려해서 정리해."
- **측정부터 했다**(어디가 비싼지 모르고 줄이면 엉뚱한 걸 줄이게 된다). 문서는 두 부류다:
  **매 세션 자동 로드**(`CLAUDE.md`, `CURRENT_TASK.md`, `.claude/rules/*`)와 **선택 로드**
  (`docs/*`, `.claudeignore`된 `PROGRESS.md`·`docs/decisions/*`). 자동 로드가 **~42k 토큰**이었고
  그중 `CURRENT_TASK.md`가 **30.8k(73%)** 였다 — 그 파일 자신이 첫 줄에 "1~2k 토큰 이하를
  유지한다"고 적어놓고 **15~30배**를 쓰고 있었다.
- **원인은 "이관이 한 번도 안 일어난 것"**: `CURRENT_TASK.md`의 "현재 작업"에 8월 항목 50여 개가
  줄줄이 쌓여 1,096줄이 됐고, 정작 이력 파일인 `PROGRESS.md`는 **7월에서 멈춰 있었다**.
  설계상 "현재 작업 → 끝나면 PROGRESS로"가 있었는데 실제로 옮긴 세션이 없었다. 규칙이 있어도
  **어디로 옮길지가 구체적이지 않으면 안 옮겨진다**는 게 이번 교훈이다.
- **정리 내용**:
  1. **`CURRENT_TASK.md` 30.8k → 1.2k**: 8월 항목 전부를 `archive/PROGRESS_2026-08.md`로
     **원문 그대로**(무손실) 옮기고, "지금 유효한 것"(현재 작업 1건·다음 우선순위·알려진 이슈·
     백로그)만 남겼다. 맨 위에 "어디서 뭘 찾는지" 표를 붙여 이 파일이 **분기점** 역할을 하게 했다.
  2. **`PROGRESS.md` 133KB → 인덱스만**: 월별 전문을 `archive/PROGRESS_YYYY-MM.md`로 쪼개고
     본체는 "어느 달에 무엇이 있는지" 표만 남겼다 — `docs/DECISIONS.md`가 인덱스+분할로
     굴러온 방식과 **같은 패턴**이다(이미 이 저장소에서 검증된 구조라 새 규칙을 만들지 않았다).
     아카이브 단위를 **반기 → 월**로 바꿨다: 반기 파일이 200KB를 넘어 한 번에 못 읽는다.
  3. **`docs/VERIFY_PENDING.md` 신설**: "배포 후 확인 필요" 80줄을 분리했다. 미확인 항목은

## D-106: 어휘 2단계 — 1단계가 동사에 몰려 있어 형용사·명사로 연다 (DAY 5~8)

**날짜**: 2026-08-28 · **관련**: D-98(도구 신설) · D-73/74(양보다 검증) · `docs/vocab-architecture.md` §7

M1(DAY 1~4)은 메커니즘을 확인하려고 만든 200단어였는데, 채우고 보니 **거의 전부 동사**였다.
접두사 계열(con·de·dis / ex·in / per·pre·pro·re)로 DAY를 나눈 결과이기도 하다. 그런데 공무원
영어에서 정답을 가르는 건 대개 동사가 아니라 **수식어와 추상명사**다 — 지문의 동사는 알아도
`adverse`·`disparity`·`stringent`를 모르면 문장이 통째로 안 읽힌다. 그래서 2단계는 "동사를 더"가
아니라 **품사를 넓히는 쪽**으로 열었다.

- **DAY 5 형용사 ①**(판단·성질) · **DAY 6 명사 ①**(제도·사회·경제) · **DAY 7 동사 ②**(1단계에서
  안 다룬 ad·circ·sub·trans 계열) · **DAY 8 형용사 ②**(정도·태도).
- 명사에 DAY를 통으로 하나 준 건, 행정·정책·통계가 소재인 지문에서 명사를 모르면 **주어와
  목적어가 통째로 비기** 때문이다.

**어원 사전이 158 → 282항목으로 늘었다.** 형용사·명사는 동사보다 어근이 흩어져 있어 재사용률이
낮다 — 이건 예상된 비용이고, 그래도 접두사 상위(`com`·`in`·`ad`·`re`·`ex`·`de`)는 여전히 20~45개
단어가 공유한다. 어근이 흐릿한 단어에 **억지 어원을 붙이지 않는다**는 D-98의 원칙은 그대로 지켰다
(2단계에서 소리연상으로 처리한 건 `bias` 하나뿐).

**철자가 같고 뜻이 다른 어근은 `in`/`in-neg`가 이미 쓰던 방식대로 id를 갈랐다** —
`par-appear`(나타나다) / `par-equal`(동등한), `nom`(법) / `nom-name`(이름),
`dis`(따로) / `di-two`(둘). form은 같으므로 화면 칩도 같게 보이고, 구분은 `ko`가 한다.

보기를 못 만드는 경우, 그리고 예문에 표제어가 다른 단어의 일부로 또 들어가는 경우

### D-107. 부부 체크 개인 결과에 심화 서술 신설 — 평소 모습 · 속마음 · 위기 대처 · 대화법
- **배경**: 사용자 지적(스크린샷 동봉) — "저 항목으로 인한 성격이나 부부로써의 태도, 성향이
  어떤지를 좀 더 자세히 말해주면 좋겠어. 하단의 설명이 좀 부실하다고 해야되나 다양하지
  않다고해야되나. 어떤 성격을 가지고 있고 어떤 생각을 하는지 위기의 상황에 어떻게 대처하는지
  좋은 대화법이라던지." 맞는 지적이다 — 개인 결과의 서술은 유형 카드 한 문단(§6.3) + 확신도
  한 줄(§5.3) + 애착 유형 한 문단(§5.4)이 전부였고, **네 성향 막대에는 설명이 아예 없었다.**
  49문항을 답하고 막대 여덟 개를 받는데 "그래서 나는 어떤 배우자인가"가 남지 않는 상태였다.
- **한 것**:
  - `BEHAVIOR_AXIS_MEANING` — 네 성향 막대 각각이 무엇을 재는지 한 줄(점수와 무관한 축 설명).
    §7-2의 "막대는 항상 문장을 동반해야 한다"를 ANX/AVO에 이어 D/I/S/C에도 적용한 것이다.
  - `BEHAVIOR_DEEP`(D·I·S·C) / `ATTACH_DEEP`(AT1~AT4) — **평소 모습 · 속마음 · 위기 대처 ·
    대화법** 네 조각을 같은 틀로. 화면에서는 성향과 애착을 조각별로 나란히 놓는다(카드
    `.cp-persona`, 접지 않음).
  - `CONFLICT_STYLES`에 `crisis`·`repair` 추가 — 갈등 접기 블록이 스타일 정의만 주고 "실제로
    뭘 하게 되는지 / 그다음에 뭘 해볼 수 있는지"는 안 주고 있었다.
- **왜 성향과 애착을 같은 네 갈래로 묶었나**: 두 체계를 각각 두 문단씩 늘어놓으면 읽는 사람이
  체계 두 개를 따로 외워야 한다. "평소엔 어떤가 / 무슨 생각을 하나 / 힘들 때 어떤가 / 어떻게
  말하면 되나"는 사용자가 실제로 갖는 질문이라, 같은 질문에 대한 두 답으로 묶으면 하나의 상으로
  맺힌다. 지적에 나열된 항목이 정확히 이 네 갈래이기도 하다.
- **왜 접지 않았나**: §7-2(D-43)는 무거움을 덜려고 접기를 도입했지만, 이번 지적은 **바로 그
  덜어낸 자리가 부실하다**는 것이다. 지적받은 내용을 접어두면 없는 것과 같다. 대신 역할·자녀
  서사와 갈등 스타일은 그대로 접혀 있어 계층 자체는 유지된다.
- **서술 규칙**(문구 뱅크 주석에 같이 적어둠): ①모든 유형에 네 조각을 **같은 틀**로 — 유형마다
  조각이 들쭉날쭉하면 어떤 유형은 대충 쓴 것처럼 읽힌다. ②강점 → 그 강점이 만드는 사각지대
  순서(약점만 나열하면 §8.5 자기비난 유발 표현 금지에 걸리고, 강점만 쓰면 읽고 나서 할 일이
  안 남는다). ③대화법은 **배우자에게 요구하는 말이 아니라 내가 해볼 말**로 — 배우자에게 바라는
  것은 이미 `DOS_*`/`DONTS_*`(§8.3)가 맡고 있어서, 여기까지 그러면 리포트 전체가 "상대가
  바뀌어야 한다"만 반복한다. ④단정형 대신 "~한 편이에요"(§2.2 — 성향 체크지 진단이 아니다).

### D-109. `cancelSpeech()`가 대기 중인 `voiceschanged` 리스너까지 지우도록 수정
- **배경**: 부부 체크 결합 기능 삭제(D-108) 작업 후 `/code-review`로 diff 전체를 훑다가 발견 —
  D-97(TTS 발음 수정)이 도입한 "음성 목록이 안 찼으면 `voiceschanged`를 한 번만 듣고 재시도"
  로직이 `.claude/rules/js-modules.md`의 "타이머·rAF·전역 리스너는 `onLeave()`에 등록" 규칙을
  어기고 있었다. 학습 화면(대화 연습·기초/초등 영어회화·복습)과 부부 테스트는 무관하지만,
  같은 브랜치의 diff를 통째로 검토하다 나온 발견이라 여기 같이 적는다.
- **버그**: `speak()`가 목록이 빈 상태에서 `speechSynthesis.addEventListener("voiceschanged", ...,
  { once: true })`로 재시도를 걸어두는데, 화면을 나갈 때 4곳의 `onLeave`가 부르던
  `window.speechSynthesis?.cancel()`은 **재생 중인 소리만 멈추고 등록된 리스너는 그대로
  둔다.** `{ once: true }`는 "한 번만 실행됨"만 보장할 뿐 실행 전 취소 수단이 아니다. 학습자가
  `voiceschanged`가 발동하기 전(세션 첫 TTS 재생 직후 흔함)에 다른 화면으로 넘어가면, 나중에
  그 이벤트가 실제로 발동할 때 **이미 떠난 화면의 문장이 지금 보고 있는 새 화면 위에서
  재생된다.**
- **수정**: 모듈 스코프 변수 `pendingVoiceRetry`에 등록한 리스너 참조를 들고 있다가,
  새로 만든 `cancelSpeech()`가 `speechSynthesis.cancel()`과 함께
  `removeEventListener("voiceschanged", pendingVoiceRetry)`도 호출한다. `speak()`가 첫 줄에서
  부르던 `window.speechSynthesis.cancel()`도 이걸로 교체해서, 같은 문장에 `speak()`를 두 번
  부르면(예: 문항 재생 중 다시 듣기 버튼 연타) 이전 대기 리스너가 자동으로 지워지고 —
  중복 재생 방지가 부수 효과로 딸려온다. `listen()`·`record.js`의 `window.speechSynthesis?.
  cancel()`과 4개 화면 파일(`basic-conversation`·`dialogue`·`elementary-conversation`(2곳)·
  `review`)의 `onLeave` 콜백도 전부 `cancelSpeech()`로 교체 — 한 곳만 고치면 나머지 세 곳이
  같은 사고를 반복한다.
- **검증**: `speak`/`cancelSpeech`는 `window.speechSynthesis`에 묶여 `node --test`로 직접
  검증되지 않았던 영역이라, `test/learning.speech.test.js`에 `EventTarget`을 흉내 낸 최소
  스텁(`FakeSynth`)을 추가해 **결정적으로** 검증했다: ①`speak()`가 목록이 비었을 때 리스너를
  걸고 ②`cancelSpeech()`가 그 리스너를 지우고 ③지운 뒤 `voiceschanged`가 와도 재생되지 않고
  ④지우지 않으면(대조군) 정상적으로 늦게 재생됨을 확인. **버그를 일부러 되살려 빨간불 확인**:
  `cancelSpeech()`에서 리스너 제거 줄만 빼니 2건 실패(늦은 재생 방지 검사·중복 리스너 방지
  검사) → 복구 후 통과. `npm test` **160/160**(신규 3개). `scripts/verify.cjs` 전체 통과,
  콘솔 에러 없음(ADHD 채점 검사 1건이 첫 실행에서 흔들렸으나 재실행 시 통과 — 이 변경과
  무관한 기존 산발적 흔들림으로 확인).
- **실기기 확인은 못 함**: 이 버그는 "음성 목록이 늦게 찬 다음 순간 화면을 떠나는" 정확한
  타이밍에서만 드러나는데, 헤드리스 Chromium은 자체적으로 비동기 `voiceschanged`를 발생시켜
  목업 타이밍과 충돌해 실제 SPA 내비게이션으로 재현하는 수동 스크립트가 신뢰할 수 없는
  결과를 냈다(D-55와 같은 한계 종류). 단위 테스트의 결정적 확인으로 대신했다.

### D-113. 결과 화면 다듬기 — 심화 서술 블록 접기 + 조사 오류 수정
- **배경**: D-107 → D-108 → D-110 → D-111 → D-112, 다섯 라운드 연속으로 "추가하자"만 하고

### D-114. 절충형(CS5) 쏠림 54%를 서술 다섯 결로 분해 — 문항·절단점은 그대로
