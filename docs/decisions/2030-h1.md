### D-103. DAY 확인 문제·빈칸 채우기가 같은 단어를 중복 채점해 SRS 간격이 부풀던 버그 수정
- **배경**: 사용자 요청으로 D-98~D-102 전체를 다시 훑었다(오류 검토 + 개선점 파악 후 수정 →
  메인 머지). 가장 심각했던 것은 **DAY 화면 안에서 같은 단어가 세 번 채점되고 있었다**는 것.
- **증상**: `renderVocabDay()`의 흐름은 단어 카드(👍/😅 자가평가) → 확인 문제(4지선다) →
  빈칸 채우기(철자) 순인데, 셋 다 `gradeWord()`를 불러 **같은 단어의 SRS 엔트리를 계속
  다시 채점**했다. 카드에서 "good"(reps 0→1, ivl=1, due=내일)까지는 의도대로였지만, 곧이어
  확인 문제에서 "good"을 한 번 더 받으면 reps 1→2·ivl=3(due 3일 뒤)으로, 빈칸까지 마치면
  reps 2→3·ivl = 3×ease ≈ 8(due 8일 뒤)로 튀었다. **DAY 하나를 처음부터 끝까지 도는
  몇 분 사이에, 아직 하루도 안 지난 단어가 "8일 뒤에나 다시 보여줄 단어"가 돼 있었다.**
  D-99·D-101·D-102에서 사용자에게 "내일 다시 올라와요"라고 설명한 것과 실제 동작이
  어긋나 있었던 셈이다 — 화면 문구는 맞았지만 그 문구가 가리키는 값 자체가 잘못 계산되고
  있었다.
- **왜 지금까지 안 잡혔나**: `state.vocab.cards`는 세션 메모리라 새로고침 전에는 눈에
  잘 안 띄고, 헤드리스 검증도 지금까지는 "화면이 뜨는가/문구가 맞는가"만 확인했지 실제
  스케줄 값(`reps`·`ivl`)을 페이지 안에서 직접 읽어본 적이 없었다.
- **원인**: SM-2류 스케줄은 "실제로 날짜가 벌어진 recall"에만 의미가 있다 — `cur.reps`가
  이전 성공 횟수를 나타내고 그 횟수만큼 간격이 기하급수로 늘어나는데, 같은 세션 안에서
  초 단위로 여러 번 "성공"을 기록하면 시간 경과 없이 reps만 쌓여 간격 계산이 그 전제를
  잃는다.
- **수정**: DAY 화면에서는 **카드 자가평가만 SRS를 건드린다**. 확인 문제(`pick()`)와 빈칸
  채우기(`grade()`)에서 `gradeWord()` 호출을 제거했다 — 정답/오답 판정과 `st.wrong`/
  `correctCount`(DAY 정답률·"틀린 단어만 다시 보기" 진입로)는 그대로 남아 있으니 DAY
  화면의 다른 기능은 전부 그대로다. "틀린 단어만 다시 보기"로 카드 자가평가를 다시 하는
  경로는 그대로 뒀다 — 그건 사용자가 명시적으로 고른 재학습이라 다시 채점되는 게 맞다.
  "오늘 학습"(`/today`)은 손대지 않았다 — 거기는 큐의 항목 하나가 정확히 한 번만
  `advance()`를 통해 채점되는 구조라 애초에 이 버그가 없었다.
- **덤으로 고친 것 셋**(같은 리뷰에서 발견):
  1. **로그인 동기화 알림 경쟁**: `initVocabSync()`가 설정(`vocab_settings`)과 일정
     (`vocab_progress`) 두 요청을 병렬로 보내면서, 화면 재렌더 알림(`notifyLearningSync`)은
     일정 쪽 요청에만 붙어 있었다 — 설정 요청이 더 늦게 끝나면 방금 로그인한 사용자의
     "하루 목표" 선택이 화면에 반영 안 된 채로 남을 수 있었다. 두 요청을
     `Promise.allSettled`로 묶어 **둘 다 끝난 뒤 한 번만** 알리도록 고쳤다.
  2. **탭 제목이 개명 전 이름을 그대로 두고 있었다**: D-101에서 화면을 "오늘 복습"에서
     "오늘 학습"으로 바꿨는데, `civilVocabScreens`의 `title`(브라우저 탭 제목)은 "오늘
     복습"에 머물러 있었다.
  3. **오늘 큐의 빈칸 모드에 null 방어가 없었다**: DAY의 빈칸 흐름(`startCloze`)은 예문에서
     표제어를 못 찾는 단어(`makeCloze()`가 null)를 미리 걸러내는데, 오늘 큐 쪽은 그 방어가
     없어서 그런 단어를 만나면 화면이 죽을 수 있었다. 지금 200단어는 전부
     `test/learning.vocab.test.js`가 통과를 보장하지만, 8000개로 늘어날 콘텐츠의 방어선으로
     오늘 큐도 null이면 고르기 모드로 자동 대체하게 했다.
- **검증**: 페이지 안에서 `state.js`를 직접 동적 import해 `state.vocab.cards`의 실제
  `reps`/`ivl` 값을 읽는 헤드리스 테스트를 새로 만들었다(지금까지는 화면 문구만 봤지 값
  자체를 검증한 적이 없었다). DAY 1(50단어)을 카드 → 확인 문제 → 빈칸까지 전부 마친 뒤
  `reps === 1 && ivl === 1`(=내일)이 유지되는 것을 확인했다. **버그를 되살려 빨간불도
  확인했다** — gradeWord 호출을 되돌리면 확인 문제 단계에서 이미 `reps`가 흔들리고
  (테스트가 무작위로 첫 보기를 눌러 오답이 섞이면서 `lapses`까지 늘어나는 걸로 나타났다),
  복구 후 다시 통과. `npm test` 217/217(순수 함수 쪽은 이번 수정과 무관해 그대로), 기존
  헤드리스 스위트·`scripts/verify.cjs` 재확인 통과.
- **손대지 않은 것**: 로그아웃 후 같은 브라우저 탭에서 다른 계정으로 로그인하면 첫 계정의
  로컬 세션 데이터(`state.vocab.cards` 등)가 초기화되지 않고 새 계정과 병합돼 버릴 수 있는
  경로를 리뷰 중에 함께 발견했다. 이건 `js/learning/cloud.js`(학습 진행률)·NumPath 마을
  동기화에도 똑같이 있는 **앱 전체의 기존 패턴**이라, 이번 어휘 도구만 따로 고치면 세
  동기화 모듈의 동작이 서로 달라진다. 별도로 논의해서 세 곳을 한 번에 정리하는 게 맞다고
  보고 이번 범위에는 넣지 않았다.

### D-104. 로그아웃해도 로컬 진행률이 안 지워져 다른 계정으로 로그인하면 섞이던 버그 수정
- **배경**: D-103 리뷰 중 발견해서 "손대지 않은 것"으로 남겨뒀는데, 사용자가 "치명적인
  오류인데 앱 전체의 기존 패턴이라도 수정해야 될 것 같다"고 판단해 이번에 바로 고쳤다.
- **증상**: `js/learning/cloud.js`(문장 도구 진행률)와 `js/learning/civil-vocab/cloud.js`
  (어휘 일정)의 로그인 동기화 로직이 로그아웃(`user === null`)을 감지하면 `syncedForUser`만
  `null`로 되돌리고, **로컬 state는 그대로 뒀다.** 그래서 같은 브라우저 탭에서 계정 A로
  공부하다 로그아웃하고 계정 B로 로그인하면: 로그인 이벤트가 오자마자 `mergeProgress()`/
  `mergeVocabCards()`가 "로컬(=방금 나간 A의 진행률)"과 "B의 서버 값"을 합쳤다. 병합
  규칙이 "더 진행된 쪽" 또는 "더 최근 응답"을 남기는 것이라, A가 더 많이 공부했거나 더
  최근에 응답했으면 **A의 진행률이 그대로 B 계정에 업서트됐다** — 서로 모르는 두 사람이
  같은 기기(도서관 PC, 학원 공용 PC, 가족 공유 태블릿)를 오가며 쓰면 실제로 벌어질 수
  있는 사고다.
- **왜 지금까지 안 잡혔나**: 두 모듈 모두 "순수 함수(`mergeProgress`/`mergeVocabCards`)만
  `node --test`로 검증하고, 나머지는 Supabase 클라이언트에 묶여 브라우저에서만 돈다"는
  이유로 로그인/로그아웃 흐름 자체는 테스트가 없었다(주석에도 그렇게 적혀 있었다). 헤드리스
  회귀도 이 샌드박스에서는 Supabase CDN이 막혀 실제 로그인·로그아웃 왕복을 재현할 수 없다.
- **수정**: 로그아웃을 감지하면(`syncedForUser`가 `null`이 아니었다 = 방금 전까지 어떤
  계정의 데이터가 로컬에 실려 있었다) 그 데이터를 **지운다**.
  - `js/learning/cloud.js`: `state.learning = {}`
  - `js/learning/civil-vocab/cloud.js`: `state.vocab.cards = {}` · `state.vocab.days = {}` ·
    `state.vocab.newPerDay = DEFAULT_NEW_PER_DAY`(하루 목표도 계정을 안 타는 값이 아니므로
    같이 되돌린다 — 안 그러면 자기 설정이 없는 다음 계정이 방금 나간 계정의 목표를 물려받는다)
  - **한 번도 로그인한 적 없는 세션은 그대로 둔다**(`syncedForUser`가 원래부터 `null`인
    경우는 지우지 않음) — 안 그러면 "로그인 전에 공부해두고 나중에 로그인해서 서버로
    올린다"는 이 앱의 핵심 흐름(D-68, D-100)이 깨진다. 로그아웃 이벤트와 "로그인한 적
    없음"을 구분하는 게 이 수정의 핵심이다.
- **테스트 가능하게 리팩터링**: 두 모듈 다 로그인 이벤트 콜백(`sync`)이 `loadCloudAuth()`로
  받아온 실제 CDN 클라이언트에 클로저로 묶여 있어 순수 함수가 아니었다. `cloud` 클라이언트를
  **인자로 받는** `makeSyncHandler(cloud)`로 빼서, `initLearningSync()`/`initVocabSync()`는
  실제 클라이언트로 이 함수를 호출하기만 하고, `node --test`에서는 최소한의 가짜
  `cloud`(로그인 상태를 흉내내는 `_login()`/`_logout()`, `select/eq/order/range/maybeSingle/
  upsert`를 체이닝만 흉내내는 가짜 `supabase.from()`)로 실제 시나리오를 검증한다.
  `syncedForUser`도 모듈 전역에서 `makeSyncHandler`의 클로저로 옮겼다 — 안 그러면 테스트
  여러 개가 그 상태를 공유해서 서로 오염시킨다.
- **검증**: 두 모듈 각각에 시나리오 테스트를 새로 만들었다 — "A로 로그인 → 로컬에 진행이
  많이 쌓임 → 로그아웃 → 로컬이 비어야 함 → B로 로그인 → B의 서버 값만 보여야 함(A의 값이
  안 섞여야 함)", "로그인한 적 없는 세션은 아무것도 안 지운다", "핸들러 인스턴스끼리
  `syncedForUser`가 안 샌다". `npm test` **222/222**(문장 도구 3개·어휘 도구 2개 추가).
  **버그를 되살려 빨간불도 확인**했다 — 로그아웃 분기의 초기화 코드를 되돌리면 "B로
  로그인했는데 A의 로컬 값이 섞여 들어왔다" 검사가 정확히 실패한다. 이 샌드박스에서는
  실제 Supabase 로그인 왕복을 재현할 수 없어 헤드리스 브라우저 검증은 못 했다 — 순수
  로직으로 옮긴 이 테스트가 지금 낼 수 있는 가장 강한 증거다.
- **배포 후 확인 필요**: 실기기에서 계정 A로 로그인해 몇 개 학습 → 로그아웃 → 계정 B로
  로그인 → 마이페이지·어휘 인트로가 **B 자신의** 진행만 보여주는지(A의 흔적이 안 남는지).
