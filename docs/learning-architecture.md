# learning-architecture — 학습 카테고리

> 선택 로드 문서. 학습 카테고리 상세를 확인해야 할 때만 읽는다. 공통 라우터 계약·모듈맵은
> `docs/architecture.md`.

## 1. 배경 · 범위 (D-60, D-63, D-64, D-65, D-66, D-67, D-68, D-69, D-70)

사용자가 준비한 "영어 학습 웹앱" 로드맵(어르신/어린이 대상, Next.js+Supabase+PG결제 풀스택
기획)을 이 저장소(빌드 없는 정적 SPA, 심리테스트/미니게임 레지스트리)의 세 번째 카테고리로
축소 적용했다. 요금제는 명시적으로 나중으로 미뤘고(사용자 지시), 그 김에 로그인·DB·SRS·결제도
함께 미뤘다 — 전부 영속 저장이 전제인데, 이 앱은 부부 체크의 KV 하나를 유일한 예외로 두고
철저히 무상태다(`CLAUDE.md` "영속 데이터" 항목).

**구조는 3단이다**: 홈 → 학습 목록(도구 카드, `/learning`) → 도구의 목차(챕터 카드, 예
`/learning/basic-conversation`) → 챕터 하나(문장 연습, 예
`/learning/basic-conversation/greeting`). 학습 카테고리 **안에는** 앞으로 다른 공부 도구가
더 들어갈 수 있어 도구 단위는 심리테스트처럼 카탈로그가 맞고, 도구 하나 **안**은 여러
상황(챕터)을 순서대로 밟아나가는 목차형 흐름이다(D-63, 아래 §2 첫 항목에 이 구조를 잡기까지의
시행착오를 적어뒀다).

**v1 범위**: 도구 하나(`js/learning/basic-conversation/` — 기초 영어회화, **7세 이하
대상**(D-69)), 챕터 4개, 총 136문장(기초 112 + 심화 24) — `greeting`(인사/기분 표현) ·
`daily-routine`(하루 일과 — 아침+식사+목욕/잠자리+위생 통합) · `family-and-me`(가족·
자기소개+색깔 통합) · `playground`(놀이터에서 — 놀이+날씨+공원 통합). 로드맵 1-2가 준
"동물/음식·학교/놀이터" 같은 단어 카테고리에서, 사용자 지시(D-65)로 "일상대화 위주,
어린이 애니메이션 참고"로 다시 짰다 — 뽀로로·타요·페파피그류가 매번 "아침에 일어나기",
"친구랑 놀기", "밥 먹기", "잠자리"처럼 하루 일과 하나를 에피소드로 삼는 것과 같은 결로,
단어 나열(This is a rabbit)보다 그 상황에서 실제로 오가는 말(Let's play! / Can I have
more?)을 우선했다. 여기서 한 번 더, 사용자 지시(D-66)로 "묶을 수 있는 건 묶어서" 8챕터를
지금의 4챕터로 합쳤다 — 시간순으로 이어지는 상황(아침→식사→목욕/잠자리)이나 소재가
겹치는 상황(가족+자기소개, 놀이+날씨)은 챕터 하나로 묶고, 그 안의 문장 개수를 늘리는
쪽으로 방향을 잡았다(아래 §2 첫 항목). 이어서 사용자 지시(D-67)로 "I like ~"·"This is
my ~"·"I want ~"·"Let's play ~" 같은 문장 틀에 단어만 바꿔 반복하는 패턴 드릴 13문장을
각 챕터에 추가했다(88 → 101문장) — 로드맵 1-2가 애초에 "만능 문장 틀 20개 우선 선정"을
제안했던 것과 같은 방향이다. 그 다음(D-69)엔 사용자가 (1) 실제로 쓰이는 자연스러운
어휘인지 검증, (2) 대상을 7세 이하로 명시, (3) 위생·공원·색깔 등 11문장 추가(101 →
112문장), (4) 한글을 아직 못 읽는 어린이를 위한 한국어 음성 지원을 요청 — 4가지를 한
번에 반영했다(아래 §2). 마지막으로(D-70) 사용자가 "7세면 실제 대화력이 훨씬 느는데
지금은 입문용 같다, 단계를 나눠서 원어민 7세 수준까지 만들어보자"고 제안 — 각 챕터
끝에 심화 문장 6개씩(총 24개, 112 → 136문장)을 이었다. 챕터 하나의 흐름은 로드맵 2-2
그대로: 카드 진입 → 듣기(TTS, 0.75배속 토글) → 말하기(STT) → 결과(Levenshtein 유사도
기반 3단계 피드백) → 다음 문장. 반복해서 챕터 하나를 끝내면 완료 화면(처음부터 다시 /
목차로 돌아가기).

## 2. 지금 어떻게 만들었나

- **도구는 레지스트리, 챕터는 데이터(D-63)**: 처음(D-60)엔 챕터 `greeting`을 최상위 도구인
  것처럼 홈 카드에서 바로 등록했다. 사용자가 "목차별로 나열할 수 없다, 하나의 공부 창이
  되어야 한다"고 지적해 레지스트리·목록을 통째로 없앴는데(D-62), 곧이어 "학습 카테고리 안에
  다른 공부 도구도 넣을 거다, 심리테스트 들어가면 종류별로 테스트가 있듯이"라는 요구가
  왔다 — 카탈로그 자체가 필요 없던 게 아니라, **카탈로그가 있어야 할 층이 한 단 아래**였다.
  지금 모양: `registerLearning`/`listLearning`(`js/core/router.js`, `registerTest`와 대칭)이
  **도구**를 등록하고, 도구 하나(`js/learning/<toolId>/`) 안의 `data.js`가 `CHAPTERS` 배열로
  **챕터(목차)** 를 갖는다. `index.js`가 `CHAPTERS.map()`으로 챕터별 화면을 자동 생성해서,
  새 챕터를 추가해도 `index.js`·라우터를 안 고친다(`docs/architecture.md` §5 참고).
- **챕터는 잘게 쪼개지 않고 묶는다(D-66)**: D-65에서 8챕터(각 8~10문장)로 짰더니 목차가
  또 하나의 스크롤 목록이 됐다 — "학습에 하나의 도구로 만들어줘야지, 목차별로 다 나열할
  수 없잖아"(D-62)의 취지가 챕터 레벨에서 다시 반복된 셈이다. 사용자가 "묶을 수 있는 건
  묶어서 한 챕터당 문항수를 늘리고 챕터가 무분별하게 늘어나서 정리 안 되는 상황을
  방지하자"고 정리해줘서, 시간순으로 이어지는 상황(아침→식사→목욕/잠자리)과 소재가
  겹치는 상황(가족+자기소개, 놀이+날씨)을 묶어 4챕터로 줄이고 챕터당 문장 수를 16~30개로
  늘렸다. **앞으로 새 상황이 생기면 새 챕터부터 만들지 않는다** — 기존 챕터 중 시간순으로
  이어지거나 소재가 겹치는 자리가 있는지 먼저 보고, 정말 별개 상황일 때만 새 챕터를
  만든다.
- **폴더**: `js/tests/<id>/`·`js/games/<id>/`와 같은 4파일 구조(`data.js`/`score.js`/
  `screens.js`/`index.js`). `score.js`는 DOM을 모르는 순수 함수(Levenshtein 유사도 + 3단계
  피드백 경계)라 `node --test`(`test/learning.score.test.js`)로 검증되고, 챕터에 무관하게
  도구 하나가 공용으로 쓴다.
- **TTS/STT**: 브라우저 내장 `speechSynthesis`/`SpeechRecognition`만 쓴다. 서버 API·어댑터
  패턴 없음 — 공급자가 하나뿐인데 인터페이스부터 만드는 건 지금 시점에 과설계다(아래 §3-2).
- **한국어 해석도 TTS로 들을 수 있다(D-69)**: 대상이 7세 이하로 좁혀지면서, 한글을 아직
  못 읽는 아이가 많다는 게 실제 문제로 떠올랐다 — 지금까지는 한국어 해석이 화면에
  텍스트로만 있어서, 못 읽는 아이는 부모가 대신 읽어줘야만 뜻을 알 수 있었다. `speak(text,
  rate, lang)`에 `lang` 매개변수를 추가해(기존엔 `"en-US"` 고정) 한국어 해석 옆의 🔊
  버튼(`#learning-listen-ko`)이 `speak(card.ko, 1, "ko-KR")`을 부르게 했다 — 영어 듣기
  버튼과 완전히 같은 메커니즘, 언어만 다르다. 자동 재생은 안 한다 — 브라우저 자동재생
  정책상 사용자 제스처 없이는 안정적으로 안 울리고, 카드를 열 때마다 매번 울리면 반복
  학습 중 오히려 방해가 될 수 있다.
- **문장 데이터 어휘 점검(D-69)**: "실제로 쓰이는 어휘인지" 요청에 맞춰 112문장 전체를
  다시 훑었다 — 전부 원어민이 실제로 쓰는 고빈도 표현이라 교체가 필요한 건 없었다(유일하게
  "Cheers!"가 또래보다는 캐주얼한 어른 말투에 가깝지만, 식사 시작 인사로 흔히 쓰여 오류는
  아니라 남겨뒀다).
- **상태**: `state.learning[chapter.id] ??= { index: 0 }` — 챕터 화면에 처음 들어갈 때
  지연 초기화된다. 몇 번째 문장인지만 있으면 된다. 듣기/말하기 결과(마이크 상태·유사도·피드백)는
  화면 지역 DOM이라 새로고침은 물론 문장 넘김에서도 굳이 state에 넣지 않았다(다음 문장으로
  넘어가면 어차피 사라질 값).
- **화면**: `disc-question`(§ architecture.md D-26)과 같은 in-place 렌더 패턴 —
  `renderChapter(chapter)`가 골격(`back-row` + `#learning-card`)을 한 번만 그리고, 문장이
  바뀔 때마다 `#learning-card`의 innerHTML만 새로 그린다. 목차 화면
  (`renderBasicConversationIntro`)은 `renderPsychList`와 같은 카드 목록 패턴을 재사용한다.
- **에러 처리**: 브라우저가 STT를 지원하지 않거나 인식이 실패하면(`onerror`) 문구로 보여주고
  `console.error`도 남긴다 — 조용히 삼키지 않는다(`CLAUDE.md` 절대 규칙).
- **마스코트 일러스트 없음(D-61 → D-64, 되돌림)**: 처음엔 `js/learning/mascot.js`가 문장
  카드 위에 인라인 SVG 얼굴(표정·소품 조합)을 그렸다. 이미지 생성 도구·파이프라인이 없어서
  코드로 그린 것이었는데, 실제로 렌더된 걸 보니 사용자가 "이모티콘이 별로"라고 판단해
  뺐다(D-64) — 이미지가 정말 필요해지면 그때 실제 이미지 에셋(사람이 그리거나 외부에서
  받은 일러스트)으로 따로 넣는다는 전제다. `mascot.js`와 문장 데이터의 `mood` 필드,
  `test/learning.mascot.test.js`는 전부 삭제했다 — 다시 만들 근거(무엇을 어떻게 그릴지)가
  아직 없는데 코드만 남겨두면 죽은 코드다.
- **건너뛰기(D-61)**: 듣기/말하기를 강제하지 않는다. 이미 아는 문장이면 `#learning-skip`
  버튼으로 마이크 없이 바로 다음 문장으로 넘어갈 수 있다. 마이크로 성공/실패 결과가 나온
  뒤에는 건너뛰기 버튼을 숨긴다(`skipBtn.style.display = "none"`) — 그 시점엔 이미 결과
  카드의 "다음 문장" 버튼이 같은 역할을 하므로, 같은 동작을 하는 버튼 두 개가 같이 보이지
  않게 했다.
- **기초 → 심화 2단계(D-70)**: 문장에 `level: "advanced"`를 붙일 수 있게 했다(없으면
  기초). 각 챕터 배열 안에서 기초를 전부 나열한 다음 심화를 뒤에 이어서, 같은 챕터를
  계속 진행하다 보면 자연스럽게 단계가 올라간다 — 새 화면도, 레벨 선택 UI도 만들지
  않았다(기존 in-place 렌더가 그대로 처리한다). 심화 문장에는 목차 화면의 카드 설명도
  "기초 N · 심화 M"으로 갈라 보여주고(`renderBasicConversationIntro`), 연습 화면에서는
  기존 `.cover .tag` 클래스(다른 테스트 인트로가 카테고리 라벨에 쓰던 것)를 그대로 재사용해
  "심화" 배지를 얹었다 — 새 CSS 없이 됐다.

## 3. 잘라낸 것 — 나중에 어떻게 붙일지

로드맵의 나머지 단계를 "안 만든다"가 아니라 "지금은 안 붙인다, 붙일 때 이렇게"로 기록해둔다.
이 저장소 관례상 되돌리거나 미룬 접근은 여기 적어두고 다시 원점에서 논의하지 않는다.

### 3-1. 로그인 · 영속 데이터 (Supabase Auth 재사용) — D-68에서 붙임
- **지금**: 로그인하면 `state.learning`이 `learning_progress` 테이블(user_id PK, RLS로 본인
  행만 select/insert/update)에 저장된다. `js/core/auth.js`가 관리자 전용 필터를 벗어던지고
  모든 로그인 사용자를 `currentEmail`로 추적하게 되면서(D-68), 로그인 자체는 일반 방문자에게
  열렸다 — `isAdmin()`은 여전히 부부 체크 게이트(D-56)용으로만 남아 있다. `js/learning/cloud.js`가
  로그인 시 서버 값을 로컬과 병합(챕터별로 index가 더 큰 쪽을 남긴다)하고, 문장이 넘어갈 때마다
  업서트한다. 로그아웃했거나 CDN이 막혀 있으면 이 앱의 다른 콘텐츠처럼 세션 한정으로만 동작한다.
- **어떻게 붙였나**: 새 로그인 시스템을 만들지 않고 `js/core/cloud-auth.js`(Supabase Auth,
  카카오·구글 OAuth)를 그대로 재사용했다 — NumPath 마을이 D-55에서 했던 것과 같은 패턴(CDN
  의존을 `cloud-auth-loader.js`의 동적 import 뒤로 숨김)이지만, 코인/마을 같은 보상 체계는
  따라가지 않았다(D-54/55에서 되돌린 건 그 부분뿐이다).

### 3-2. STT/TTS 공급자 교체 (어댑터 패턴)
- **지금**: `speechSynthesis`/`SpeechRecognition` 호출이 각 도구의 `screens.js`에 직접 있다.
- **나중에 붙일 때**: 두 번째 공급자(OpenAI Whisper, ElevenLabs/Azure Speech 등)가 **실제로**
  필요해지는 시점에 `speak(text, rate)`/`listen(onResult, onError)` 두 함수를 인터페이스로
  놓고 구현체를 갈아끼운다. 도구가 늘어도 이 두 함수는 도구마다 거의 같은 모양이라, 그때는
  `js/learning/`에 공용 모듈로 뽑는 편이 나을 수 있다. 공급자가 브라우저 API 하나뿐인 지금
  만들면 쓰이지 않는 추상화가 된다 — 로드맵 3-2의 "확장형 어댑터 패턴"을 선반영하지 않은 이유.

### 3-3. 간격 반복(SRS) · 학습 기록 DB
- **지금**: 틀린 문장을 따로 추적하지 않는다. 세션 내에서 몇 번이고 다시 들을 수 있을 뿐이다.
  D-67의 패턴 드릴(같은 문장 틀 반복)은 한 세션 안에서의 반복일 뿐, 여러 날에 걸쳐 다시
  보여주는 진짜 간격 반복(SRS)의 대체물이 아니다 — 둘은 서로 다른 걸 최적화한다(문장 틀
  숙달 vs 장기 기억 정착). SRS 없이도 패턴 드릴 자체는 유효하니 먼저 넣었을 뿐이다.
- **나중에 붙일 때**: `Learning_Logs`(로드맵 5-2)를 로그인 이후에나 의미 있는 기능으로 미룬다 —
  익명 사용자에게 SRS를 붙이려면 결국 기기 로컬(`localStorage`)에 "복습 필요" 문장 id 목록을
  두는 절충안이 되는데, 이건 부부 체크의 KV 예외처럼 "영속 데이터 없음" 원칙에 새 예외를
  만드는 결정이라 가볍게 넣지 않는다. 로그인이 붙은 뒤 서버 쪽에 붙이는 게 순서상 맞다.

### 3-4. 결제 · 요금제
- **지금**: 없음(사용자 지시로 명시적 보류).
- **나중에 붙일 때**: 이 저장소에 유료 결제가 들어오는 건 처음이라, 붙일 때 포트원/토스페이먼츠
  SDK 연동 방식과 "무엇을 Free/Pro로 가를지"(도구 개수 제한? 챕터 개수 제한? 고품질 음성?)
  부터 다시 정해야 한다 — 지금 만든 v1은 사용자가 이미 정한 무료 정책(로드맵 1-3, 하루 3개
  상황·10~15문장) 중 "무료"쪽만 반영했고 유료 갈림길 자체가 아직 코드에 없다.

### 3-5. 새 도구 · 어르신 모드
(챕터 추가·교체·병합은 더 이상 "잘라낸 것"이 아니다 — 챕터를 늘렸다(D-65) 줄였다(D-66)
하며 이미 이 구조로 여러 번 해봤다. `js/learning/basic-conversation/data.js`의 `CHAPTERS`에
항목만 추가·수정·병합하면 목차 화면·화면 등록이 자동으로 반영된다는 게 실전으로 확인됐다.
새 챕터를 만들 때의 기본값은 이제 "먼저 기존 챕터에 붙일 자리를 본다"다(D-66, 위 §2).)
- **새 도구(다른 과목, 예: 숫자 배우기)**: `js/learning/<newToolId>/`를 통째로 새로 만들고
  `registerLearning`으로 등록한다 — 학습 목록에 카드가 하나 더 생긴다. 심리테스트에 검사
  하나를 추가하는 것과 완전히 같은 절차(`docs/architecture.md` §5).
- **어르신 모드**: 새 카테고리를 또 만들지 않는다 — 학습 목록에 "기초 영어회화(어르신용)"
  같은 별도 도구로 넣거나, 같은 도구 안에 모드 선택을 두는 두 방향이 있는데 아직 결정 안
  했다(실제로 만들 때 판단). UI 원칙 자체는 다르다(대형 버튼·고대비·한글 발음 가이드
  병기) — 챕터 데이터에 `ko` 옆에 `pron`(한글 발음 표기) 필드를 추가하는 정도로 화면 분기
  없이 처리될 것 같다.
- **8~9세용(더 큰 아이)**: D-69에서 대상을 "7세 이하"로 명시하면서, 로드맵 원래 페르소나
  (5~9세)보다 좁아졌다. D-70의 심화 단계(원어민 7세 수준 의견·비교·협상 문장)가 이 격차를
  어느 정도 메웠지만, 8~9세 전용 콘텐츠(더 긴 문장, 더 복잡한 문법)가 따로 필요해지면
  새 도구로 분리하는 쪽이 맞아 보인다 — 같은 도구 안에 난이도를 셋 이상 섞으면 목차
  카드 하나의 "기초/심화" 구분이 다시 흐려진다. 확정 아님, 실제로 필요해질 때 판단.

### 3-6. 광고 슬롯
- **지금**: 학습 목록(`learning-list`)에는 다른 목록처럼 배너가 있다. 목차 화면과 챕터
  화면(연습 화면)에는 없다.
- **나중에 붙일 때**: 다른 게임 결과 화면처럼 `adSlotMarkup()`/`adGateMarkup()`을 완료
  화면(`showDone()`)에 붙이면 된다 — 이미 있는 부품이라 새로 만들 게 없다. 파일럿 단계라
  검증 전에는 넣지 않았을 뿐이다.

### 3-7. 다중 턴 대화형 학습
- **지금**: 없음. 문장 하나를 듣고 그대로 따라 말하는 구조뿐이다(질문→대답→되묻기 같은
  주고받기 없음).
- **왜 지금 안 만들었나(D-70)**: 원어민 7세의 진짜 대화력(상황에 맞게 대답을 스스로
  구성하고, 상대 말에 반응해서 되묻는 것)은 "정해진 문장 하나를 얼마나 똑같이 따라
  했는가"로 채점하는 지금 방식과 아예 다른 문제다 — 채점 기준부터(정답이 여러 개일 수
  있다), 화면 흐름부터(문장 하나가 아니라 대화 트리) 다시 설계해야 한다. 그래서 이번엔
  "같은 상황의 문장을 더 어렵게" 정도로 타협했다(위 D-70의 기초/심화 2단계).
- **나중에 붙일 때**: 사용자 의견 — "대화형 웹앱은 추후에 구축". 지금 도구(`basic-conversation`)를
  고쳐서 넣기보다, 학습 목록에 완전히 새 도구로 추가하는 쪽이 맞아 보인다(§3-5의 "새 도구"
  절차 그대로) — 지금 도구의 "문장 하나 = 카드 하나" 모델과 근본적으로 다른 화면·채점
  구조가 필요해서, 기존 도구를 무리하게 확장하면 두 모델이 한 폴더에 뒤섞인다. 확정 아님,
  실제로 만들 때 화면 구조부터 다시 설계.

## 4. 배포 후 확인 필요

- **실기기 음성 인식**: 헤드리스 브라우저는 마이크·네트워크가 없어 `SpeechRecognition`이
  실제로 동작하는지 확인하지 못했다(가짜 STT를 주입해 판정 로직 자체만 검증). iOS
  Safari·Android Chrome에서 마이크 권한 승인 흐름, 인식 정확도, 첫 시도 지연을 확인 필요.
- **`speechSynthesis` 실기기 음질·속도**: 0.75배속 재생이 실제 목소리로 자연스럽게 들리는지
  기기별 확인 필요(브라우저 내장 TTS라 기기·OS마다 목소리가 다르다).
